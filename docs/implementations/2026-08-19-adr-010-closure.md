## Implementation approach

The closure is an attestation, so the "implementation" is the evidence
chain. Two independent claims had to be established, each traced to a
single shipped definition rather than to documentation:

1. **The three input dimensions.** `BasicCalibrationVectorizer`
   (`calibration/features.py:42`) implements the
   `CalibrationFeatureExtractor` ABC from `interfaces.py`. Its
   `feature_names` property returns the module-level constant
   `_FEATURE_NAMES` (line 23), and `output_dim` returns the literal `3`
   (line 54). `extract` builds its return array from exactly three
   `np.mean` calls in that order (lines 84-91), so the names, the
   declared dimension, and the actual vector layout are mutually
   consistent by construction — there is no code path that emits a
   fourth component or reorders the three.

2. **The 27-rule arity.** `TSKRuleBase.from_grid`
   (`fuzzy/tsk.py:185-224`) appends one `TSKRule` per element of
   `itertools.product(*per_input_mfs)`. The rule count is therefore the
   cardinality of that Cartesian product; see the next section.

Both claims were then checked empirically against the installed package
(read-only; no file written, no LOCKED module touched) so that the
attestation rests on executed behavior and not only on code reading.

## Mathematical / Statistical details

Let `d` be the number of input dimensions and `K_i` the number of
membership functions supplied for dimension `i`, so that `per_input_mfs`
is the family of sets `M_1, …, M_d` with `|M_i| = K_i`.

`from_grid` iterates `product(M_1, …, M_d)` and appends exactly one
`TSKRule` per yielded tuple, with no filtering, deduplication, or early
exit. The number of rules is therefore the cardinality of the Cartesian
product,

    n_rules = |M_1 × M_2 × … × M_d| = prod_{i=1}^{d} K_i

which is the standard product rule for counting: each of the `d`
coordinates is chosen independently, so the choices multiply. For the
ratified baseline `d = 3` and `K_1 = K_2 = K_3 = 3`:

    n_rules = 3 × 3 × 3 = 3^3 = 27

Three properties of this construction are worth recording, because they
are what make the ratified number *stable* rather than incidental:

- **Completeness.** `itertools.product` enumerates every combination, so
  the rule base covers the full grid — no antecedent combination is
  silently absent.
- **Distinctness.** `product` never repeats a tuple, so the 27 rules have
  pairwise-distinct antecedent tuples. (Verified below by counting
  distinct antecedent identity-tuples: 27, matching `n_rules`.) A
  degenerate `per_input_mfs` that passes the *same* MF object twice
  within one dimension would still produce 27 rules, but only because
  `product` counts positions, not values — the baseline supplies three
  distinct MFs per dimension, so this edge case does not arise here.
- **Independence from `output_dim`.** The consequent parameter matrix has
  shape `(output_dim, input_dim + 1)` per rule; `output_dim` affects the
  size of each rule's consequent, never the rule count. The verification
  below deliberately uses `output_dim = 2` (unequal to 3) so that a
  spurious dependence on `output_dim` would be visible.

Note that `prod_i K_i` grows exponentially in `d` — adding a fourth
dimension at `K = 3` would give 81 rules, and each rule carries an
`(output_dim × (d+1))` consequent matrix. This is the concrete cost that
any future ADR-013 proposal for a larger dimension set must justify. It
is recorded here as context, not as a decision; ADR-010 ratifies `d = 3`.

## Design decisions

- **Ratify both halves in one entry rather than splitting them.** The
  Context line coupled them ("a 3×3×3 grid over three input dimensions.
  Which three is itself open"), so closing one and leaving the other
  would have left the same self-contradiction in a different sentence.
- **State the ADR-010 / ADR-013 boundary explicitly.** ADR-013 is still
  `Open / Deferred`. Without a boundary clause, a reader could take
  "ADR-010: Accepted" as foreclosing the vectorizer comparison entirely.
  The added sentence ratifies the baseline while preserving ADR-013's
  right to propose alternatives. *Alternative considered:* leave ADR-010
  silent and let ADR-013's own text carry the boundary — rejected because
  the ambiguity lives in ADR-010, so the disambiguation belongs there.
- **Note that re-arity is configuration, not code.** `from_grid` is
  already parameterized by `per_input_mfs`, and the pre-existing
  Consequences line already said "Adding more inputs is a `from_grid`
  argument away." Making this explicit in the Decision paragraph
  pre-empts a future reader concluding that changing the grid requires
  editing the LOCKED module — which would wrongly invoke the two-owner
  lock procedure for what is a call-site change. *Alternative
  considered:* restrict the entry strictly to 27 — rejected as it would
  leave that misreading available.
- **Do not add a 3×3×3 regression test in this PR.** `tests/test_tsk.py`
  currently pins only a 2×3 = 6 grid. A test asserting 27 would be
  test-only and would not touch the LOCKED module, but the issue scopes
  this closure to the ledger; the gap is queued as a follow-up instead.
- **Do not fix the drift found along the way.** Four divergences surfaced
  (see `docs/audits/2026-05-25-followup-issues.md`). Folding fixes into a
  ratification PR would mix an attestation with behavior/documentation
  changes and make the owner sign-off harder to audit.
