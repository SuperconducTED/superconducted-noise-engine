# 2026-09-03: phase-3 plan and ticket set

## Problem / Motivation

Cycle 2 closed without the results it planned for: the 630-snapshot floor was counted
in the wrong unit, the trainer (ADR-014) was never started, the membership-function
ablation (ADR-019) never ran, and T1 vs IT2 (ADR-009) stayed Open. The 2026-08-30
handoff document that opened phase 3 established that the binding blocker was never
data: ADR-019 waits on a manual parameterization nobody owned, and ADR-009 waits on
ADR-019. Phase 3 needs a plan that turns that into sequenced, owned, gated work with a
trained model measured by 2026-09-30, and one ticket per assignment in the form the
team already uses (#48).

## Implementation approach

Documentation and orchestration only; no source change. The plan was written from the
2026-08-30 handoff document, the ADR ledger at `7d39a2b`, the open issue and PR state on
2026-09-02/03, and the source tree. Seventeen premises the plan relies on were each
checked adversarially against the code and the live repository (a scratch venv at
`C:\sc-venv`, qiskit 2.4.1 / qiskit-aer 0.17.2, 280 tests passing) before any ticket was
drafted. Each of the ten drafted tickets then went through an independent adversarial
review under three lenses in one pass (factual references against the repo and `gh`;
ownership and process rules against `docs/team.md`; feasibility and internal
consistency against the milestone sequencing) and a fix pass applying the findings. A
separate cross-ticket critic then read the full set of ten and reported fourteen
contradictions, seventeen file collisions, five milestone gaps, twelve missing-work
items and a per-person load check; the lead ruled on every one of those and applied the
rulings to every affected ticket, directly repairing the one ticket (#57) an automated
editing pass was interrupted while writing. The ticket bodies follow the structure of
#48: why, what, how, functional and non-functional requirements, a use-case diagram,
design with the mathematics stated in plain English, sign-off decisions, ordered
implementation steps, a testing convention, a definition of done, and the expected
result.

Six ticket bodies exceeded GitHub's 65,536-character issue-body limit; each was split at
a top-level section boundary, with the remainder posted as the first comment and both
halves saying so explicitly.

## Design decisions

- **A trained model by 2026-09-30 does not wait on the snapshot floor.** ADR-019's own
  gate note says its remaining prerequisite is a manual parameterization, which has no
  data dependency; ADR-009 waits on ADR-019. The floor is treated as a claim gate (what
  the results doc may say), never an implementation gate (what work waits on).
- **The trainer is type-agnostic.** Both shipped defuzzifiers are linear in the
  consequent parameters (verified: weighted-average and Nie-Tan reduce to one design
  matrix with different effective per-rule weights, to machine precision), so the
  trainer is built now rather than after ADR-009 decides T1 vs IT2.
- **A units defect found while planning is filed separately, not folded into the
  ticket set.** `BasicCalibrationVectorizer.extract` returns microseconds where the
  loader and every consumer assume seconds; on real archived data the ratified 3x3x3
  grid fires at exactly zero and the pipeline raises. This blocks nobody in phase 3
  because every membership-function grid in the plan is derived from the archive's own
  measured quantiles rather than from the affected `FEATURE_SCALES` constant, but it is
  a real defect in shipped code and is tracked as issue #66.
- **Ten cross-ticket contradictions were resolved by fiat rather than left as open
  questions in each ticket.** Where two tickets proposed different names, signatures or
  locations for the same interface (the reference-noise-model builder, the trained-model
  JSON schema, the training-package layout, where Dr. Akba's answers are recorded), the
  lead picked one and applied it everywhere, because leaving it as a shared sign-off
  question across two tickets is how a contract drifts before either PR lands.
- **Four load-driven descoping decisions.** The critic's per-person load check put every
  contributor at or above their four available weeks before counting reviews. The lead
  moved #53's execution to himself, marked the pre-gate/between-gates fuzzification
  ticket (#65) as phase 4, split the seven-shape membership-function parameterization
  into a four-shape M1 delivery plus a three-shape follow-up, and batched the canonical
  desktop verification runs into two sessions instead of one per PR.

## Verification

- Baseline: `C:\sc-venv\Scripts\python.exe -m pytest tests/ -q -o addopts=""` collected
  and passed 280 tests on `main` at `7d39a2b`, agreeing with NC-021 (280 at `947fe3d`).

  confirmed as written, thirteen needed a correction that is recorded in each ticket

  against `snapshots/2026-08/ibm_fez/20260831T203902000000Z.json`, the loader path
  returns `mean_T1 = 1.214277e-04` s and the vectorizer `1.214277e+02`, and constructing
  the shipped 3x3x3 ensemble against that snapshot raises
  `ZeroDivisionError: WeightedAverageDefuzzifier received all-zero firing strengths`.
- Issue filing: `gh issue list --repo SuperconducTED/superconducted-noise-engine
  --milestone "Phase 3 · ANFIS results"` lists nine issues (#56-#64), each with the
  assignee the plan's section 4 names; #65 exists with no milestone; #66 exists with no
  milestone. Every drafted ticket's cross-references to the other nine were rewritten
  from `T-KEY` placeholders to real issue numbers and spot-checked for none remaining.
